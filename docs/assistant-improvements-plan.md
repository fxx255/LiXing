# AI 学习助手：公式、通信框图与后续优化方案

本文记录上一阶段的公式修复、通信框图与当时提出的后续方案。用户现已授权实施提速、缓存、中断重试和后台保护，并在验收后发布 GitHub 新版及更新云端版本；新的执行范围与验收门槛见 [实施及发布细则](assistant-runtime-implementation.md)。下方“仅方案”和未发布记录保留为上一阶段事实，不再作为本轮禁止实施或发布的指令。

## 1. 公式修复

已从用户备份中只读提取 9 月 20 日 10:57 的原回答。完整公式含成对的 \left 和 \right；截图中的省略号是报错占位组件截断了源码，不能据此认定原式缺括号。

实际问题发生在窄屏长公式分行：普通 trim 将段末的反斜杠加空格（LaTeX 间距命令）裁成了孤立反斜杠。Markwon 块解析器再补上换行后，JLatexMath 无法解析。修复按完整间距命令裁剪，并区分奇数、偶数个连续反斜杠，保留合法行分隔符。

验收使用原始数学表达式、多个显示宽度及 Markwon 实际传入渲染器的源码（包含换行）。旧代码对照的两项验收均失败；修复后的结果见文末。不会改数字、增删括号或修改历史数据库。

## 2. 通信框图

用户 20:36 的回答用代码块拼接 ASCII 框图，窄屏下会散乱。新增 diagrams 结构，由模型提供节点、连线和简短标签，App 在本地排版绘制：

- 矩形功能块、圆形乘法器/加法器、输入输出文字和分支点。
- 左到右主链、上下辅助支路、分支合流、明确的入出端口、虚线和短连线标签。
- 中文、内嵌 LaTeX 公式、副标题；文字和公式共同参与尺寸测量。
- 连线按正交路径避让节点。画布保持内容比例，高分辨率 PNG 可点击进入现有图片查看器。
- 图像存于应用文件目录；通过已有图片备份链路保存。当前设备还保存结构副本，可在 PNG 丢失但副本存在时重画；结构副本本身不承诺随备份迁移。
- 曲线图和框图每轮按 plots、diagrams 顺序编号，再按生成轮次追加。失败图位保留，避免后续图号错位；未设锚点的图片放在正文末尾。

协议限制：每轮最多 4 张框图，每图最多 24 个节点、40 条连线，标签 60 字符、标题 40 字符。超限标签、重复 ID、未知端点等拒收并提示，不截断公式或影响正文。首版支持 LR 主链，TB 明确拒收。复杂密集图仍建议拆成数张子图；不保证自动排版达到专业电路 CAD 的编辑能力。历史 ASCII 回答保持原文，需要重新让助手生成才能得到新框图。

## 3. 回复速度与思考长度（仅方案）

代码中流式正文事件目前只切换“已开始回答”状态，正文需等当前轮 JSON 解析完成才显示。这会增加“思考很久但没有输出”的体感；应与供应商真正的推理时间分开诊断。

建议顺序：

1. 先记录请求开始、首个思考片段、首个正文片段、正文可见、请求完成的时间；按模型分组统计，不记录密钥和完整私聊。
2. 对 reply 字段做增量解码并节流刷新正文；未闭合的 JSON、LaTeX、表格保持稳定占位，不能把 reasoning 当正文。计划变更仍等完整解析后进入确认。
3. 沿用现有思考强度设置，逐个适配供应商实际支持的参数。普通问答默认适中，复杂推导由用户选择较高强度；不盲目压缩数学推理或降低输出长度上限。
4. 把自动续写造成的额外请求次数纳入耗时统计，防止短输出反复续写。先有测量，再调整阈值。

验收：同一组普通问答、长推导、图片题目，比较正文首次可见时间和总完成时间；推导、公式和计划确认功能保持正确。

## 4. 缓存命中率（仅方案）

现在固定协议在最前，随后是精确到分钟的时间、用户偏好、思考指令、本机数据、历史和当前提问。动态时间不一定让前面的固定协议缓存失效，但会截断后续可复用前缀；本机上下文变化、网关路由、模型版本、供应商缓存 TTL、图片请求也会影响命中。

建议把固定协议、稳定的用户偏好和思考设定前置；把当前时间与当前数据快照放在历史之后、当前问题附近，并明确这是只读上下文。序列化顺序保持稳定，避免无意义的空白和字段顺序变化。联网/工具声明也尽量稳定。

先采集供应商 usage 中可用的 prompt_tokens、cached_tokens 或 prompt_cache_hit_tokens；按供应商口径和模型分别统计，用“缓存输入 token 总数 / 输入 token 总数”计算加权比例。字段缺失显示“未提供”，不能算 0%。不能承诺 50% 或任何固定命中率，也不能为了缓存发送过期计划或删除必要上下文。

## 5. 中断后的回旋箭头（仅方案）

在输入框左侧增加重试入口，但前提是先持久化“在途请求”：

- 请求 ID、会话 ID、原始文本、附件的稳定文件路径、模型选择、上下文快照、已生成正文、状态和时间。
- 状态：生成中、已完成、已中断、主动取消。进程重启时将未完成请求标为中断；切换会话后仍能找到对应请求。
- 仅存在可重试的中断请求时显示回旋箭头。点击复用原请求和附件，正在重试时禁用连续点击；新输入的草稿保留。
- 默认重新生成这次回答，在同一个回答位置更新并标明状态，不能把残缺 JSON 当最终答案。原用户消息不重复插入，部分回答保留至重试成功。
- requestId 用于本地幂等；供应商不支持幂等请求时，网络超时后的重试仍可能产生二次计费。计划动作继续走用户确认，并以动作批次 ID 和事务防止重复执行。
- 删除会话、主动取消、缺失附件应有独立处理，不能无条件自动重发。

验收：断网、超时、切换会话、划走任务、系统回收、应用重启、连续点重试、图片请求及待确认计划。

## 6. 后台保护（仅方案）

已有生成期间的前台通知服务，但网络请求仍由 ViewModel 协程持有。单纯把服务改成 START_STICKY，无法恢复丢失的那次请求。

建议将生成任务交给应用级任务管理器或前台服务持有，由页面订阅进度；页面切换不再决定请求生命周期。与第 5 项共用持久化记录，发生回收后能够说明状态并提供重试。按 Android 版本处理前台服务启动限制、通知及 dataSync 类型时限，必要时使用有超时的唤醒锁，确保完成、取消、错误时释放。

从最近任务划走是否终止服务因系统/厂商而异，不应一概承诺。用户“强制停止”后无法保活；系统回收、断网和厂商省电策略也无法完全规避。核心目标是减少中断并让中断可恢复，不做永久常驻服务。

推荐后续实施顺序：耗时/缓存诊断 → 在途请求与草稿持久化 → 重试入口 → 任务移出 ViewModel → 增量正文展示和参数调优。
