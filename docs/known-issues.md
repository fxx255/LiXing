## #A 长气泡内表格「被撑得很宽、拖不动、看不见内容」

**状态**：宽度那条**根因已确认**；拖不动找到一条**新的强嫌疑**并给出真机验证方法。
**按用户指示暂不改代码**（2026-09-16：「先记录吧先不改也可以」）。

### 现象（用户原话）
> 在较长回答气泡中有概率显示不出生成的图像，靠后的表格也无法拖动，其实表格有些时候
> 每隔宽度富裕很多，但是依然控了很大，还拖不动，导致看不见内容。

拆成三条独立症状：
1. 长气泡内生成的图像有时不显示
2. **靠后的表格拖不动**
3. **表格宽度「富裕很多」却仍被撑得很大**

### 用户补充确认（2026-09-16）

| 问题 | 回答 |
|---|---|
| 拖不动是「完全没反应」还是「能拖一点弹回」？ | **完全没反应** |
| 窄表格（两三列短文字）也会被撑宽吗？ | **会** |
| 有稳定复现的题目吗？ | 没有特定题目，但**只要输出一长就稳定出现** |

这三条把排查范围收窄了很多：
- 「窄表格也撑宽」⇒ **宽度策略本身就是无条件撑宽**，与表格内容无关（见下，已确认根因）
- 「完全没反应」而不是「弹回」⇒ 不像「滚动区间为 0 后回弹」，更像**触摸根本没被处理**
- 「长输出必现」⇒ 与**输出长度**强相关，指向**随块数增长**的开销，而不是某个固定布局 bug

### 症状 3：根因已确认 —— `TABLE_WIDTH_FACTOR` 无条件撑宽

`AssistantScreen.kt:1516`
```kotlin
/** 含表格时表格画布相对气泡宽度的放大倍数：先给列宽更多空间，仍放不下再横向滑动。 */
private const val TABLE_WIDTH_FACTOR = 1.8f
```

`AssistantScreen.kt:1722`
```kotlin
val tableWidthPx = (containerWidthPx * TABLE_WIDTH_FACTOR).toInt()
```

`containerWidthPx` 来自 `Modifier.onSizeChanged`（第 1706 行），即**气泡正文实际可用宽度**。
⇒ **无论表格实际需要多宽，一律按 1.8 倍画布渲染**，没有「够用就停」的分支。

设计初衷没问题（让窄气泡里的单元格不至于被压成一团），但缺了「够用就停」：
两三列短文字的表格本来 0.5 倍气泡宽就够，也被拉成 1.8 倍 ⇒ 正是用户说的
「宽度富裕很多，但是依然控了很大」；右侧一大半在屏幕外，于是「看不见内容」。

**修法方向**（未实施）：先按原始宽度试排，量出表格真实内容宽，只在
`内容宽 > 气泡宽` 时才撑，且撑到刚好够用，上限仍 1.8 倍。
代价是新增一次「试排 → 测量 → 重排」的往返，而表格量高的时机本来就脆弱（见下）。

### 症状 1+2：新发现的强嫌疑 —— 高度轮询把主线程榨干了

⚠️ **这是本轮最有价值的发现**：三条症状（图不显示 / 图点不开 / 表格拖不动）
**很可能是同一个根因**，而且能同时解释「完全没反应」和「长输出必现」。

`MarkdownChunk` 里有个高度守望循环（`AssistantScreen.kt:1814-1850`），
每块内容起一个协程反复测量真实高度：

```kotlin
val deadline = System.currentTimeMillis() + HEIGHT_WATCH_WINDOW_MS   // 12_000L
while (System.currentTimeMillis() < deadline) {
    delay(if (stablePolls >= HEIGHT_STABLE_POLLS) HEIGHT_HEARTBEAT_MS else HEIGHT_POLL_INTERVAL_MS)
    val latest = view.measuredHeightCompat(renderWidthPx)            // ← 每次都是一次完整 measure
    ...
}
```

而 `measuredHeightCompat`（第 1931 行）**不是读缓存，是真量**：

```kotlin
measure(widthSpec, heightSpec)   // EXACTLY 宽 / UNSPECIFIED 高 ⇒ 完整重建 StaticLayout
return measuredHeight
```

对带大量 span 的长 Markdown TextView，一次 `measure()` 就是一次**完整文本排版**，
几毫秒到几十毫秒不等，且**同步跑在主线程**。

三个因素叠加，开销随「输出长度」爆炸：

1. **几乎每块都在轮询**。循环入口的守门条件是
   `if (!isTableBlock && !mayRenderLatex(content)) return`，
   而 `mayRenderLatex` 只是 `content.contains('$')` —— 数学回答里几乎每块都有 `$`
   ⇒ **所有块都进循环**，不只是表格。
2. **流式期间 12 秒的 deadline 永远到不了**。`LaunchedEffect(host, content, ...)` 的 key
   含 `content`，**每来一个 token 就取消重开**，deadline 从零重算 ⇒ 生成多久就轮询多久。
3. **停在 100ms 快档下不来**。只有高度连续 5 轮不变才降到 400ms 心跳；流式期间内容
   一直在长、高度一直在变 ⇒ `stablePolls` 反复归零，**始终 100ms**。

保守估算：15 个块 × 10 次/秒 = **主线程上每秒约 150 次完整 TextView 排版**，
贯穿整个生成过程。**主线程被饱和 ⇒ 输入事件延迟/丢弃**，表现就是：
触摸完全没反应（表格拖不动、图片点不开）、图像加载/解码拿不到主线程（图不显示）。

这也解释了为什么 v1.0.35 → v1.0.37 连修三轮触摸属性都没根治 ——
**很可能一直追错了方向**：不是「谁吃掉了触摸」，而是「触摸根本没被处理」。

### 🔬 真机验证方法（很便宜，建议下次上机时做）

**回答生成完之后，干等约 15 秒，再去拖那个表格。**

- **如果等一会儿就能拖了** ⇒ 上面的轮询假设成立。修的方向是降低测量频率/开销
  （例如：只在内容停止变化后开轮询、按块数退避、复用 ViewTreeObserver 的
  `OnPreDraw` 回调代替定时轮询、或让 `measuredHeightCompat` 在宽度未变时读缓存）。
- **如果等 15 秒仍然完全没反应** ⇒ 与主线程无关，回到「触摸路由」方向继续查。

顺带可以同时观察：轮询期间整个气泡是不是**连页面纵向滚动都发涩**？
如果是，主线程饱和基本坐实。

### 已排除 / 已修的方向（避免重复走）
- v1.0.23：`SelectionContainer` 包住整个气泡，装了自己的 `pointerInput` 并把事件
  标记为已消费 ⇒ 内层滚动与点击都失效。**已修**（现在只包纯文字）。
- 高度上报：曾用「只增不减」，宽度变化时高度不会变小 ⇒ 真实 View 的 bounds 长期
  占着偏大的高度，把下方兄弟的触摸吃掉。**已修**（改为跟随最新测量）。
- 槽位复用：`chunks.forEachIndexed` 未加 key ⇒ 图文交替时按位置复用，内层
  AndroidView 错配。**已修**（加了 `key(index)`）。
- 表格行高：`TableRowSpan.getSize()` 只在首次绘制时填 `layouts`，为空则整行算 0 高，
  且 Android 复用旧 Layout 不重算 ⇒ 必须 `setText(getText())` 强制重排。**已修**
  （轮询补发重排，最多 `TABLE_REPOLL_MAX = 8` 次）。

### 一处自我更正（先前推测有误）
之前怀疑 `clipToBounds()` 排在 `horizontalScroll()` 之后是「顺序反了」。重看之后：
Modifier 链里它在 `horizontalScroll` **内侧**，裁的确实是内容，方向没错。
但它裁的是**内容自己的尺寸**（1.8 倍宽），而不是视口（1 倍宽）⇒ 对「溢出到气泡外」
这个原定目标其实是**空转的**。属于**观感问题**，与「拖不动」无关，优先级低。

## #B 长气泡靠后位置，生成的图片点不开

**状态**：**按用户要求先记录、暂不修复**（原话：「如果暂时没有发现，可以先记录，先不修了」）。

### 现象
长回答气泡中，**靠后**位置的生成图无法点开查看；靠前的图正常。多轮反馈未彻底解决。

### 三轮修复史（都已上线，仍未根治）

|---|---|---|
| v1.0.35 | 图片 View 漏关 `isLongClickable` | 关掉 |

### 目前最可能的机制
见 #A —— 主线程被高度轮询饱和后，触摸与图像加载都会「静默失效」。
这条比之前三轮的触摸属性理论更能解释「长输出必现」。

`onTouchEvent` 覆写对**所有**块生效（含表格），只在真的按到 `ClickableSpan`

异常都 `return false`（宁可链接点不到，也不吃触摸）。
⇒ 若真机验证排除了主线程因素，再回来细看这条。

## #C `**加粗**` 在回答里看不出效果

**状态**：**渲染管线已证明正常，需用户提供原始文本才能继续**。

### 已完成的排查（结论明确）
用真实 Markwon 渲染 + AST 探针，逐层验证：

1. **解析层正常**：`MarkdownBoldRenderTest` 确认 AST 里确实生成了 `StrongEmphasis` 节点。
2. **span 层正常**：渲染出来的 `Spanned` 上挂的是
   `io.noties.markwon.core.spans.StrongEmphasisSpan`
   （注意：**不是** `StyleSpan`——第一次按 `StyleSpan` 断言得到 `spans=0` 是假红），
   且覆盖区间精确（`**abc**` ⇒ `[2,4]`）。
3. **星号被正确消费**：文本里不会残留 `**` 字面量。
4. **边界情况都有覆盖**：中文紧贴星号、混排含标点、多段各自独立、未成对不误判、
   内侧带空格不误判——7 项全绿。

⇒ **渲染层无法解释该现象。** 剩下的可能只在两处：

- **字体层**：当前正文字体（项目自带字体或系统中文字体）没有真正的 bold 字重，
  `Typeface.DEFAULT_BOLD` 被回退成常规字重 ⇒ 有加粗 span 但视觉无差别。
  ⚠️ 这条**在 Robolectric 上验证不了**：Robolectric 不栅格化，
  `Typeface.DEFAULT_BOLD.isBold` 恒为 `false`（空壳），任何字重型断言都是假绿/假红。
  必须真机肉眼看，或查字体资源里是否存在 bold 变体。
- **内容层**：模型输出的其实不是 `**…**`（比如用了全角 ＊、或者 `**` 与文字之间
  被插入了不可见字符）。这是最常见的情况，**但从截图看不出来**。

### 需要用户提供（关键）
- [ ] **出现该问题的原始回答文本**（长按复制出来的纯文本，不是截图）。
  拿到就能立刻判定是内容层还是字体层——用 `contains("**")`
  和字符码点一看便知。
