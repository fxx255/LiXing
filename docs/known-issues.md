## #A 长气泡内表格「被撑得很宽、拖不动、看不见内容」

**状态**：已定位到两个可疑点，**等真机确认后再动手**（用户指示：先别急着改）。

### 现象（用户原话）
> 在较长回答气泡中有概率显示不出生成的图像，靠后的表格也无法拖动，其实表格有些时候
> 每隔宽度富裕很多，但是依然控了很大，还拖不动，导致看不见内容。

拆成三条独立症状：
1. 长气泡内生成的图像有时不显示
2. **靠后的表格拖不动**
3. **表格宽度「富裕很多」却仍被撑得很大** ← 这条是新增信息，指向宽度策略本身

### 已查到的代码事实

**第 3 条的根因基本可以确定：`TABLE_WIDTH_FACTOR = 1.8f` 是无条件撑宽。**

`AssistantScreen.kt:1516`
```kotlin
/** 含表格时表格画布相对气泡宽度的放大倍数：先给列宽更多空间，仍放不下再横向滑动。 */
private const val TABLE_WIDTH_FACTOR = 1.8f
```

`AssistantScreen.kt:1722`
```kotlin
val tableWidthPx = (containerWidthPx * TABLE_WIDTH_FACTOR).toInt()
```

`containerWidthPx` 来自 `Modifier.onSizeChanged`（第 1706 行），即**气泡正文实际可用宽度**。
于是：**无论表格实际需要多宽，一律按 1.8 倍画布渲染。**

设计初衷是好的——「先给列宽更多空间，仍放不下再横向滑动」，为的是让窄气泡里的
单元格（尤其行内公式）不至于被压成一团。但它没有「够用就停」的分支：

- 一个只有两列短文字的表格，本来 0.5 倍气泡宽就够，仍会被拉成 1.8 倍 ⇒ 用户看到的
  「宽度富裕很多，但是依然控了很大」。而且因为内容确实宽了，视口里只能看到左半部分，
  右侧留白在屏幕外，观感就是「又宽又空还看不全」。
- 用户还必须手动横拖才能看到右半——如果拖不动，那就彻底看不见内容了。

**这条要修的话，方向是「按需撑宽」**：先按原始宽度试排，量出表格的真实内容宽
（Markwon 表格能给出列宽合计），只在 `内容宽 > 气泡宽` 时才撑，且撑到刚好够用为止，
上限仍为 1.8 倍。但这需要新增一次「试排 + 测量 + 重排」的往返，
而表格量高的时机本来就脆弱（见下），因此**必须先真机确认症状 2 和 3 的关系**再动。

**第 2 条（拖不动）的可疑点：`clipToBounds()` 排在 `horizontalScroll` 之后。**

`AssistantScreen.kt:1735-1743`
```kotlin
Box(
    modifier = Modifier
        .wrapContentWidth()
        .zIndex(FIGURE_Z_INDEX)
        .horizontalScroll(scroll, reverseScrolling = false)
        .clipToBounds(),
) {
```

Modifier 链的语义是「左边的先应用、包在外层」。这里 `horizontalScroll` 在
`clipToBounds` **之前**，意味着 `clipToBounds` 作用在**滚动容器的子节点**上——
裁的是自己，等于没裁。如果原意是「裁掉溢出视口的部分」（第 1732-1734 行注释
明确说要裁，免得溢出画到气泡外面盖住文字），那这个顺序很可能是**反的**，
推测应该是 `.clipToBounds().horizontalScroll(...)`。

⚠️ 但这条**不能只凭读代码就改**：既有注释（第 1727-1730 行）说这两个条件
「缺一个就拖不动」，说明历史上这里反复调试过，顺序可能是有意为之或者
与别处的裁剪配合。改动前需要真机验证，并且要有能复现「拖不动」的样本。

### 历史上已排除的方向（避免重复走）
- v1.0.23：`SelectionContainer` 包住整个气泡，装了自己的 `pointerInput` 并把事件
  标记为已消费 ⇒ 内层滚动与点击都失效。**已修**（现在只包纯文字）。
- 高度上报：曾用「只增不减」，宽度变化时高度不会变小 ⇒ 真实 View 的 bounds 长期
  占着偏大的高度，把下方兄弟的触摸吃掉。**已修**（改为跟随最新测量）。
- 槽位复用：`chunks.forEachIndexed` 未加 key ⇒ 图文交替时按位置复用，内层
  AndroidView 错配。**已修**（加了 `key(index)`）。
- 表格行高：`TableRowSpan.getSize()` 只在首次绘制时填 `layouts`，为空则整行算 0 高，
  且 Android 复用旧 Layout 不重算 ⇒ 必须 `setText(getText())` 强制重排。**已修**
  （轮询补发重排）。

### 需要用户提供
- [ ] 「拖不动」是**完全没反应**，还是**能拖一点然后弹回**？
- [ ] 出现问题的表格，是**窄表格也被撑宽**，还是只有宽表格？
- [ ] 有没有能稳定复现的题目 / 回答文本？（有样本才敢动手，否则改了也只是赌）

## #B 长气泡靠后位置，生成的图片点不开

**状态**：**按用户要求先记录、暂不修复**（原话：「如果暂时没有发现，可以先记录，先不修了」）。

### 现象
长回答气泡中，**靠后**位置的生成图无法点开查看；靠前的图正常。多轮反馈未彻底解决。

### 三轮修复史（都已上线，仍未根治）
| 版本 | 怀疑点 | 处置 |
|---|---|---|
| v1.0.35 | 图片 View 漏关 `isLongClickable` | 关掉 |
| v1.0.36 | 关属性的时机在 `setMovementMethod` **之前**，被后续调用重置 | 调整时机 |
| v1.0.37 | 触摸被上层文本 View 的溢出区吃掉 | 重写 `onTouchEvent` |

### 目前最可能的机制（推断，未证实）
`AndroidView` 的真实高度与 Compose 给它的格位不一致时，多出来的部分会覆盖下一个兄弟
（通常是图片），把触摸吃掉。高度上报已经改了多轮（含 `clipToBounds`、`zIndex` 兜底），
但 Compose 的**测量时序**本身决定了：`factory` 先给一个空视图 → Compose 先测 →
内容之后才写入。只要这个顺序还在，就存在「某一帧报的高度偏小」的窗口。

若日后要重新追，建议的切入点是**记录型探针**：在真机上把每个 chunk 的
「Compose 格位矩形」与「真实 View 的 bounds」都打出来，直接看哪一块越界吃了触摸，
而不是继续猜。

### 需要用户提供
- [ ] 一张能复现的**长回答截图**（能看到图片位置与周边文字/表格的相对关系）
- [ ] 该回答是在**流式输出过程中**点不开，还是**输出完成后**也点不开？

## #C `**加粗**` 在回答里看不出效果

**状态**：**渲染管线已证明正常，需用户提供原始文本才能继续**。

### 已完成的排查（结论明确）
用真实 Markwon 渲染 + AST 探针，逐层验证：

1. **解析层正常**：`MarkdownBoldRenderTest` 确认 AST 里确实生成了 `StrongEmphasis` 节点。
2. **span 层正常**：渲染出来的 `Spanned` 上挂的是
   `io.noties.markwon.core.spans.StrongEmphasisSpan`
   （注意：**不是** `StyleSpan`——第一次按 `StyleSpan` 断言得到 `spans=0` 是假红），
   且覆盖区间精确（`**abc**` ⇒ `[2,4]`）。
3. **星号被正确消费**：文本里不会残留 `**` 字面量。
4. **边界情况都有覆盖**：中文紧贴星号、混排含标点、多段各自独立、未成对不误判、
   内侧带空格不误判——7 项全绿。

⇒ **渲染层无法解释该现象。** 剩下的可能只在两处：

- **字体层**：当前正文字体（项目自带字体或系统中文字体）没有真正的 bold 字重，
  `Typeface.DEFAULT_BOLD` 被回退成常规字重 ⇒ 有加粗 span 但视觉无差别。
  ⚠️ 这条**在 Robolectric 上验证不了**：Robolectric 不栅格化，
  `Typeface.DEFAULT_BOLD.isBold` 恒为 `false`（空壳），任何字重型断言都是假绿/假红。
  必须真机肉眼看，或查字体资源里是否存在 bold 变体。
- **内容层**：模型输出的其实不是 `**…**`（比如用了全角 ＊、或者 `**` 与文字之间
  被插入了不可见字符）。这是最常见的情况，**但从截图看不出来**。

### 需要用户提供（关键）
- [ ] **出现该问题的原始回答文本**（长按复制出来的纯文本，不是截图）。
  拿到就能立刻判定是内容层还是字体层——用 `contains("**")`
  和字符码点一看便知。
