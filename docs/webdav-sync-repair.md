# 坚果云多端同步修复记录

用户反馈：两台设备均为 1.0.43，另一台通过坚果云获取数据，每日打卡、历史打卡与计划不一致。以下问题已通过本地 Room 数据库和模拟 WebDAV 服务复现，不代表已核查用户坚果云中的真实文件。

## 已确认的问题

1. 旧版本迁移数据的 `sync_modified_at` 为 0。原合并规则把“不存在的记录”也视为版本 0，再比较设备编号，导致一部分设备拒收自己完全没有的计划、模板和历史记录。
2. 两端独立物化同一天同一模板时使用随机任务编号，撞上 `(date, template_id)` 唯一索引；成就、餐次与积分去重也存在类似冲突。
3. 导入失败或日志解析失败后仍可能推进对端游标，后续增量同步不再补收漏掉的记录。
4. DAO 写回尚未刷新同步版本号的旧实体时，原触发器误把真正的业务改动当成内部版本更新，导致记录版本回退、改动不上传。
5. 第三台设备转发记录时没有保留原始修改设备，时钟相同时的冲突结果会随转发者变化。
6. 自动同步只关注本机变化；只读设备不定期拉取。跳过或失败前清除了待同步状态，网络恢复后可能没有重试。
7. 餐食照片路径排除传输，但本地字段不允许 NULL，新增餐食记录会导入失败。
8. 失败也会更新“上次同步”时间；没有发现其他设备时仍可能显示“数据已是最新”。账户/目录切换没有隔离游标。多条 active 计划的查询未指定顺序，各设备可能显示不同计划。

## 修复行为

- 本地没有记录且没有删除墓碑时接收远端记录，包括版本 0 的历史数据。
- 新物化任务使用模板与日期确定的稳定编号；既有不同编号的同一任务按业务键匹配，在本地保存编号对应关系。专注、积分及删除操作沿用这个对应关系，不改写现有本机照片路径，不按相似标题擅自合并不同计划。
- 只有一台对端的快照与日志全部成功处理后才推进其游标；一台失败不阻断其他设备。新版首次运行重新读取历史基线与日志，补收旧版本误跳过的数据，并重发本机完整基线；自动修复前也尝试创建本机恢复点。
- 触发器按业务列更新计时，不再依赖 DAO 携带的旧同步版本号；只改内部版本列不会递归计时。业务内容无变化时不制造新版本。
- 同步信封增加可选原始修改设备字段，在本机独立元表保存。仍使用协议 1、数据库 13，旧字段兼容；所有设备应更新到包含本修复的版本以使用一致的合并规则。
- 启动、回前台、空闲改动触发同步，前台每两分钟拉取；失败退避重试，不丢待同步状态。遵守自动开关与 Wi-Fi 限制，手动同步仍不受网络类型限制。
- 恢复备份时，业务数据、同步墓碑/别名清理和时钟追平放在同一事务中；同步来源信息、凭据与身份不随版本备份搬运。
- 只有成功才更新“上次完整同步”；显示发现的其他设备数量和错误原因。切换账户或目录时重读基线；多个 active 计划以稳定顺序选取，保留原有数据。

## 验证

新增回归覆盖历史版本 0 的完整计划与已完成任务、旧游标修复、旧实体写回、失败重试、三设备转发、独立生成的每日任务及专注/积分引用、照片保留、餐食记录、活动计划顺序、恢复后时钟和墓碑，以及只读设备定期拉取与离线重试策略。

测试仅使用独立测试数据库和模拟服务；未修改用户坚果云文件，也未使用另一台模拟器。

完整 622 项单元测试通过，失败、错误、跳过均为 0；Debug 安装包构建和串行 `lintDebug` 通过。修复随 1.0.44 发布，正式包与云端清单验证另见该版本发布记录。
