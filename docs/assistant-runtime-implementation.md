## 一、已确认的代码问题

1. `AssistantModelClient` 已发出 `AnswerDelta`，但 `AssistantViewModel.runChatTurn` 仅切换 `activeAnswerStarted`，整轮解析完成才展示正文。服务器首个正文与用户首个可见正文之间存在可消除的等待。
2. `buildSystemPrompt` 在用户偏好之前加入精确到分钟的时间；当前本机数据又位于历史消息之前。这截断了后续稳定前缀的缓存机会。不能据此断言供应商缓存一定失效或承诺固定命中率。
3. DeepSeek Responses 联网路径当前使用完整响应读取，不是真正逐片到达。两种协议必须分别验收，不能把完成时补发一次事件算作流式提速。
4. `send`、照片入口和 `runChatTurn` 的任务、进度与页面状态绑定。现有前台服务只是保活通知，不能替代独立任务所有权。
5. 会话仓库可以追加消息、更新确认信封，没有在途请求、固定回答位置或恢复状态。仅加重发按钮会造成重复消息、丢附件、重复确认等问题。
6. 当前 Room schema 为 13，用户消息与待确认信封已持久化；日常同步有自己的时钟与变更处理。新任务状态要与跨端消息同步明确分离。

## 二、任务管理与持久化（先实现这一层）

建议新增 `AssistantGenerationManager`（应用级单例）和 `AssistantRequestRepository`，由前者以 `SupervisorJob` 管理生成，由后者管理本机请求记录。ViewModel 负责用户意图和订阅，不得把捕获 ViewModel / 页面 `_state` 的闭包放进全局协程假装完成迁移。

### 状态与原子性

- 请求至少包含 requestId、conversationId、userMessageId、answerMessageId、attemptId、状态、创建/更新时间、当前阶段、已确认轮次正文、当前轮部分正文、图槽位、附件引用和重试所需快照。
- 状态至少区分 PREPARING、RUNNING、INTERRUPTED、COMPLETED、CANCELLED。模型恢复请求、自动续写属于同一个逻辑请求的不同阶段/轮次，不能再次插入用户消息。
- 每次重试使用新的 attemptId；晚到的旧回调必须同时校验 requestId、attemptId 和运行状态，不能覆盖新结果。
- 创建用户消息、预留回答 ID 和创建请求记录应在一个本地事务内完成。记录落盘后才调用网络，持久化失败时保留输入草稿并报错。
- 第一版保持全应用最多一个活动生成任务，避免跨页重复创建任务。不能因另一个会话正在运行而把其回答更新进当前会话。
- 回答落库与 COMPLETED 应原子提交。重启时只把确实遗留、没有活跃所有者的 PREPARING/RUNNING 转为 INTERRUPTED，不能把当前进程正在执行的任务标成中断。
- 成功正文进入现有聊天与同步链路；进行中的碎片、重试快照、诊断不进入坚果云增量同步或跨设备自动执行。删除会话时取消对应任务并清理其记录，不让迟到写入重新创建已删除会话。

### 快照、附件与草稿

- 快照保存提交时的原文、模型/端点身份、推理与联网设置、必要历史及只读上下文、照片路由和稳定本地附件引用。不要持久化 API 密钥、Authorization、整份偏好文件或重复 base64 图片。
- 运行时从既有凭证存储取密钥；模型/端点配置已不可用时给出可理解的说明，不能静默把旧题目发往另一个供应商。
- 附件在首次发送前复制或固定到 App 私有持久目录；重试不能依赖短时 URI 授权和缓存文件。验证当前及历史必要附件，缺失时提示重新选择，不能偷偷变成纯文本题目。
- 保存原上下文用于恢复；重试时刷新当前日期与易变的计划/任务数据，并重新校验动作 ID，避免第二天仍执行“今天”的旧计划。历史题目和原始附件不变。
- 重试不清空用户正在编辑的新草稿；切页/恢复后的草稿行为必须可预测。按会话保存草稿与待发送附件引用，删除会话时清理，已被发送/历史使用的附件不能误删。
- 部分正文按节流策略持久化（例如每 500–1000ms，阶段变化和终态立即写）；在 IO 调度器执行，避免每 token 写数据库。
- 建议用本地 Room 新表保证事务和外键：新增 13→14 迁移、schema 导出与升级测试，不允许 destructive migration。若选择其他原子存储方案，先解释与消息事务一致性及崩溃恢复如何保证。
- 备份导入/恢复不能把历史在途状态变成待执行网络任务。保留已有备份格式兼容；任务表和凭证快照默认不导出，必要时明确处理临时表/外键约束。

## 三、中断重试与确认动作

- 输入框左侧显示回旋箭头，仅当前会话最新未完成且可重试的请求出现；无中断时不占据一个常驻提示行。内容描述为“重新发送”，点击后立即防重入。
- 点击重试复用原用户消息和回答 ID。失败前的部分答案保留为中断内容，重试进行时清楚标注状态；不能先清空它然后重试又失败而丢失所有输出。
- 新一轮部分正文可独立显示为重试进度，成功后替换同一个回答位置。最终只能有一条用户消息和一个对应回答位置。
- 如果中断后用户已另发新问题，旧请求不应从输入栏插队重放；以明确规则将其变为历史中断记录。保留原记录供回看，不能混入新问题的生成任务。
- 区分网络失败、服务超时、无有效正文、主动取消、附件缺失、配置失效。用户取消后不自动重发；重启后不自动调用模型，也不无限循环收费请求。
- 网络层取消要真正取消 OkHttp Call/流读取，不能只取消 UI 协程。CancellationException 应继续传播，finally 中释放资源。
- 计划与英语动作只从完整且有效的回复中解析，仍需用户确认。未闭合 JSON、部分正文、推理通道都不能触发动作。
- 不依赖列表下标或“这个会话所有非空信封”做新重试的动作定位；以固定消息/请求批次 ID 更新信封。保留用户先前对确认按钮的正常逻辑。
- 审核现有已应用标识与事务：快速双击确认、重启后确认、重试后的迟到回调，都只能执行一个批次一次。已应用批次不能因为重试覆盖成未应用。若存在已确认副作用，禁止普通重试覆盖该答案，提供明确状态。
- 本地幂等不等于供应商计费幂等；不添加未经供应商支持的请求字段，也不声称超时后的重试一定不重复计费。

## 四、正文提速、推理分离和耗时诊断

### 增量正文

- 从正式 answer/content 流中识别顶层 JSON `reply` 字符串，用有状态增量解码器，不用一个跨整个 JSON 的正则。只展示字符串值，不展示外层 JSON、plan_actions、plots、diagrams 或内部控制标记。
- 覆盖转义引号、连续反斜杠、换行、Unicode 转义和跨 chunk 的代理对；不会把 LaTeX 的反斜杠裁坏。同一输入按不同 chunk 切分应产生完全相同的最终正文。
- 支持现有协议允许的 JSON 围栏与解析恢复路径；不从任意嵌套对象的 reply 或 reasoning 中抓取正文。
- 未闭合公式、代码块及表格行可以暂存安全边界/占位，不能触发整页报错或显示 LaTeX 错误红框。完整段落及时显示，最终以正式解析器结果校正一次。
- UI 更新节流约 50–100ms；不在主线程每 token 重建所有公式或绘图。长回复用递增状态，控制重复扫描与字符串复制成本。
- 自动续写保持一个回答气泡、既有数学边界合并和图槽位偏移规则；下一轮思考区域不得盖住已生成正文。图像在结构完整后绘制，保留失败图位和点击放大行为。
- `[[NEED_PLAN_CONTEXT]]` 的前缀不应在流式 UI 一闪而过；计划补上下文重试时撤回控制用占位，不能让重试把真实已生成正文重复追加。

### 推理、协议兼容与速度

- 推理事件与正文事件分离；“只有推理没有答案”最终应是可恢复失败或现有有界答案恢复，绝不直接把推理链作为用户答案。
- 沿用用户明确选择的推理强度及供应商能力判断；不一律压缩必要推导、不盲目降低输出上限。审计现有 reasoning-only 恢复和自动续写的上限与取消路径，记录额外请求次数。
- Chat Completions 逐片处理；DeepSeek Responses 若端点支持流式则解析实际事件及最终 usage/citations，若不支持保留完整响应兼容路径并明确记录非流式。不能擅自改变联网方式或丢来源。
- 上下文选择、看图转写、联网、首轮生成、恢复和续写各阶段分别计时；先找出额外串行调用，不直接删除必要本机数据选择或已有多模态功能。

### 最小诊断

- 记录请求开始、首个推理、首个 answer 字节、首个可见正文、完成/中断的相对时间；以单调时钟计算耗时，以 requestId、模型/端点类型区分。
- 不记录 API 密钥、完整题目、原始聊天/推理、URL 查询参数和附件内容。诊断存储有数量/大小上限，可在已有诊断入口提供简短汇总，不新增助手底部常驻提示。
- 模拟流测试中，完整可见正文应在最后一个 SSE 事件前出现；收到可展示正文后约 300ms 内更新（用可控时钟验证，不用脆弱真实睡眠断言）。实际服务端速度需实测，不凭模拟测试声称“整体快了几倍”。

## 五、缓存优化与统计

- 稳定前缀顺序：固定协议 → 稳定用户资料/推理设定 → 稳定历史。当前时间、最新只读学习数据靠近当前问题，明确数据仅作为上下文，不能覆盖系统规则。
- 同时调整 Chat Completions 的 messages 与 DeepSeek Responses 的 instructions/input；保持角色及图片归属，不能把当前图片附在额外的恢复指令上。
- 使用统一纯函数组装消息，注入 Clock 供测试；序列化与集合排序稳定。不为了命中率发送过期数据、不扩大原有历史隐私范围。历史窗口滑动、模型或图片变化造成的缓存差异须如实保留。
- 解析供应商提供的 usage：prompt_tokens / input_tokens、prompt_cache_hit_tokens、prompt_tokens_details.cached_tokens / input_tokens_details.cached_tokens 等，按具体路径建立夹具，不靠随意猜字段。
- streaming usage-only 末块和 Responses completed 都要处理。支持的端点可请求 usage，兼容端点不支持时使用有界降级；不能因此重复一个已开始输出或已计费的请求。
- 同一请求的累计 usage 只能统计一次，不能把累计块相加。恢复/续写按各实际 HTTP 请求计数；input/cached 缺失、负值或口径冲突视为未知/不可用，不冒充 0% 或 100%。
- 按供应商/模型统计“有效 cached 输入 token 总数 ÷ 同批有效 input token 总数”，报告有效样本覆盖率；无缓存字段的调用单列“供应商未提供”，不放入零命中分母。
- 用相同历史、不同时间/本机上下文验证稳定前缀逐字一致；同时验证当次日期、计划 ID 和图片确实更新。不能保证任何固定缓存命中率。

## 六、后台保护与资源回收

- 网络生成任务属于应用级管理器，页面销毁、切页或旋转只取消订阅，不能取消正在进行的生成。用户点击取消、删除会话或服务明确超时才终止相应任务。
- 在前台用户触发发送时及时启动已有 dataSync 前台服务，通知打开应用后回到对应会话；保留原通道。完成、异常、取消和恢复失败时停止通知/服务，不永久驻留。
- 审核 begin/end 引用计数及竞争条件：启动失败后不能把其他任务的保护扣掉；任务结束与另一个开始交错时不能停错服务。可以改为按 requestId 持有令牌。
- Android 12+ 前台服务启动限制、Android 13 通知权限、Android 14 服务类型要求和 Android 15 dataSync 超时均有处理。超时回调应停止服务、取消网络并尽力保存中断状态。
- 如需要唤醒锁，仅在活动生成期间使用有明确超时的 PARTIAL_WAKE_LOCK，并在所有出口释放；不能每 token 无上限续锁。拒绝启动保护时请求仍有明确状态，不能崩溃。
- 不以 START_STICKY 代替恢复协议；不请求关闭系统所有省电限制，不承诺强制停止后继续执行。不可避免的进程终止通过持久记录恢复重试入口。

## 八、验收通过后由 DSH 发布

开始发布前重读 `docs/release.sh`、`docs/release-1.0.43.md`、`cloudbase/update-check/README.md`，以实际状态和本节安全要求修正文档中陈旧示例。不要直接运行包含强推标签、切换公开状态等旧兼容补丁的整段脚本。

1. 更新本轮和累积更新的发布说明，包括坚果云、公式和通信框图；明确旧保存 PNG 不会自动变成新绘图。只提交本任务相关文件，不提交用户备份、聊天提取、设备包、密钥、诊断原文或本地配置。
2. 固定发布提交，包名继续为 `com.example.lixing.debug`；保留仓库签名及 ARM64 正式包设置。数据库升级不清空数据。所有发布测试须针对最终提交/实际发布包，改代码后重新执行受影响验证。
3. SHA-256、字节数、versionCode/versionName/minSdk 都从最终 APK/代码核对；验证证书与 1.0.43 一致。归档 R8 mapping 到 Git 忽略的按版本目录。
4. 生成合法 update.json，apkUrl 是 GitHub 干净直链，不带镜像前缀，force=false。先创建 draft，再上传 APK 与清单，核对 GitHub 独立 digest；创建精确指向发布提交的新标签，不强制覆盖已有标签。
5. 发布并核对 latest、tag 指向、两项资产下载 URL、清单 SHA-256 与包版本；遇到网络超时先查询是否成功，不能盲目重建/覆盖 Release。PR 如确需创建则按当前任务规则附加到任务；默认遵从已有 main 发布流程。
6. 云端要更新的是当前实际启用的 `update-check` 版本服务，不是仓库内未使用的 `ai-assistant` 代理方案，也不改百度 OAuth。保留其他环境变量与鉴权设置。
7. 优先核验现有函数能获取新的 latest 清单；有管理访问能力时同步更新 `UPDATE_MANIFEST_JSON` 内联兜底为同一份正式清单。只有源码确需修复时重新部署函数。不要为了满足“更新云函数”的措辞部署无关代码。
8. 独立请求公开 `/update/check`，核对新旧 versionCode 参数场景、ok/versionName/code/apkUrl/hash/size 与 fallback/cached 状态；按代码现有缓存规则等待/重新验证，不随意填假高版本测试生产环境。
9. 通过真实下载直链/应用镜像验证安装包，校验下载后哈希、签名、覆盖安装与启动；如某条链路不可达，明确记录，不拿 Release 页面可见替代下载验收。
10. 发布交付报告包含提交、标签、GitHub Release/下载链接、云端返回结果、包大小/哈希与验证证据。若 GitHub 已发布但云端失败，明确报告部分完成并继续修复，不能宣称全部完成。缺少云管理登录时报告准确缺口，不索要明文密钥。

## 九、恢复 Bridge 后的首个派发内容

指定 `agent=dsh`、`cwd=F:\APP`、`model=wb-gateway/cn:hy4-preview`、`user_requested=true`，限流时按第一节切换用户允许的模型。要求读取本文件并实施第二至第七节；按模块完成代码及定向测试，再执行全量验证，必须完成全部授权范围。当前只到本地候选包及验收报告，不发布、不推送，等待协调者的验收结果。保留现有 dirty work，独占构建，不使用其他模拟器。完成后协调者给出具体复核意见，最多三轮整改，再根据实际情况接管必要修正。验收通过后再派发第八节；用户已授权发布，无须重复请示。
