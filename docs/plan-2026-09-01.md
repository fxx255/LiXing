# 砺行 AI 学习助手改进计划

待办日期：2026-09-01
状态：**待用户确认，先不修改**

本计划针对用户提出的三个问题：

1. Markdown 表格显示为原始文本（`| 命题 | 关键差异 | 结论 |` 这种），需要更美观；
2. 计划修改 / 英语积累等需要确认的动作，目前回复一回来就自动跳到全屏确认页，希望改为在对应回答气泡下挂一个提示按钮（不用「审核」这个词），可以先读 AI 回答，需要时再点进入；没有待确认内容时按钮不显示；计划与英语积累各一个按钮；
3. 小概率在「生成最终答案」阶段直接闪退（如 2.jpg 这道题），需排查。

---

## 1. 表格渲染优化

### 现象
截图中 `| 命题 | 关键差异 | 结论 |` 这种 Markdown 表格被原样输出为带 `|` 的纯文本，没有边框、没有列对齐。

### 根因
`ui/screen/assistant/AssistantScreen.kt::MarkdownAnswer` 构造 Markwon 时只注册了：
- `MarkwonInlineParserPlugin`
- `JLatexMathPlugin`

**没有 `MarkwonTablesPlugin`**，因此 Markwon 不会把 GFM 表格渲染成 `TableLayout`，直接当纯文本输出。

### 计划
1. 在 `gradle/libs.versions.toml` 加 `markwon-tables` 版本/库别名（版本对齐 `4.6.2`）。
2. `app/build.gradle.kts` 加 `implementation("io.noties.markwon:ext-tables:4.6.2")`。
3. `MarkdownAnswer` 工厂中追加 `.usePlugin(MarkwonTablesPlugin.create(context))`。
4. 让深色背景下的表格边框/背景也跟主题走；如果默认主题太亮，必要时给 TablesPlugin 一个 dark theme。
5. 顺手测一下对齐（`|:---:|---`）是否生效；不行再补 `MarkwonConfiguration` 的 `linkResolver` 之类。

## 2. 确认入口改为气泡下的提示按钮（不使用「审核」一词）

> 用户反馈：「审核」这个词不好听；入口只在**有需要确认的内容时**才显示；计划归计划、英语积累归英语积累，**各自一个按钮，不合并**。

### 现状
- `AssistantViewModel.send()` / `performPhotoSend()` 收到带动作的回复后，**自动**把 `planReviewOpen` / `englishReviewOpen` 置为 `true`，整屏被 `PlanChangeReviewPage` / `EnglishChangeReviewPage` 占据。
- 列表里另有一个独立的「待确认」入口卡片（`PendingPlanReviewEntry` / `PendingEnglishReviewEntry`），作用重复。

### 用户期望
- 回复出来后**不自动跳转**，可以先读 AI 的回答；
- 在产生这条动作的**那条 assistant 气泡下面**挂一个按钮；
- **没有待确认内容时按钮完全不渲染**（不留占位、不显示「暂无」）；
- 计划修改和英语积累**各显示各的按钮**，不合并成一条；
- 用词不用「审核」，换成更自然、更主动的说法。

### 命名备选（待用户确认其一）

| 场景 | 方案 A（推荐） | 方案 B | 方案 C |
|---|---|---|---|
| 计划修改 | 📋 查看计划调整（3 项） | 📋 确认计划调整（3 项） | 📋 计划调整方案待确认 |
| 英语积累 | 📖 查看英语积累变更（5 条） | 📖 确认英语积累（5 条） | 📖 英语积累变更待确认 |

推荐 A：动词是「查看」，语气最轻，不逼用户立刻做决定；括号里带条数，一眼知道量级。
页面标题沿用现有的「计划修改方案」/「英语积累变更」，两处都不出现「审核」。

### 计划
1. `AssistantViewModel`：
   - 移除 `send()` / `performPhotoSend()` 末尾 `planReviewOpen = previews?.isNotEmpty() ?: ...` / `englishReviewOpen = ...` 的**自动置位**；
   - 保留 `pendingActions` / `pendingEnglishActions`，`*ReviewOpen` 一律默认 `false`；
   - **新增归属索引**：`pendingActionsOwnerIndex` / `pendingEnglishOwnerIndex`（生成动作时记下当时 `state.messages` 的下标），这样即使待确认项来自较早的回复、用户滚上去了，按钮也挂在**正确的那条气泡**下面，而不是永远挂最后一条；
   - 按钮回调沿用已有的 `openPlanReview()` / `openEnglishReview()`。
2. `AssistantScreen`：
   - 新增 `AssistantMessageActionBar` composable，仅在 `index == ownerIndex` 的那条 assistant 气泡下方渲染；
   - **空状态不渲染**：`pendingActions.isEmpty()` 时计划按钮整体不出现，`pendingEnglishActions.isEmpty()` 时英语按钮整体不出现，两者互为独立；
   - 两个按钮用 `FilledTonalButton` / `OutlinedButton`，各自 `onClick` 直接进对应确认页（状态互斥逻辑已存在）；
   - **删除**列表顶部那个独立的「待确认」卡片（`PendingPlanReviewEntry` / `PendingEnglishReviewEntry`），避免和气泡下按钮重复，入口唯一。
3. 用词清理：把界面上所有「审核」字样（按钮、Snackbar、标题）替换为上表选中的说法。
4. 不影响：
   - `applySelected` / `applySelectedEnglish` / `dismissPendingActions` 等逻辑保持；
   - 本地校验与幂等保护保留。

## 3. 闪退排查

### 现象
用户拍 2.jpg（教材：含反例题 15/16 和带 `\frac{(\cos x - e^{x^2})\sin x}{2+1-\sqrt{x^2}}` 等多重 LaTeX）发给 AI，模型在「生成最终答案」时偶发闪退。

### 根因分析（按可能性排序）

#### 3.1 主要：JLatexMath 解析失败未兜底
`MarkdownAnswer` 用 `io.noties.markwon:ext-latex:4.6.2`：
```
JLatexMathPlugin.create(this.textSize) { builder -> ... }
```
没有传 `errorHandler` 也没有 `errorText`。模型偶尔输出的 LaTeX 经常不是完全合法的，例如：
- 漏右括号 / `}` 数量不对；
- `\begin{aligned}` 块前面有非法字符；
- 残存的 `\tag{}`（已清洗但偶尔漏网）；
- 数学里嵌套 `\text{...}` 内含 `$`。
JLatexMath 在解析时会抛 `ParseException`，markwon-ext-latex 默认 `LatexUtils.textDrawable` 把 `ParseException` 包成 `RuntimeException` 抛出来；
`Markwon.setMarkdown` 在 UI 线程未捕获 → **app crash**。

#### 3.2 次要：`wrapLongFormulas` 的 `$$` 状态机不健壮
- `line.trim() == "$$"` 才切 display；如果模型输出 `  $$ `（带缩进/空格）/` $$ `，状态机不会切换，块永远不关；
- 累积整个未关闭块，最后通过 `splitFormulaBlocks` 重新包 `$$`，但中间已经过 `sanitizeAssistantLatex`，可能 `convertAlignedEnvironments` 又把未关闭的块当成普通行处理 → 进入 Markwon 的 `$$` 不是合法 LaTeX → 触发 3.1。

#### 3.3 次要：`transformEnvironment` 边界
- `aligned` 块里如果 `&` 计数异常（转义 `\&`、空行、`\hline`），生成的 `array` 列说明符可能为空或太长，JLatexMath 解析炸 → 3.1。
- `rows` 为空时已经原样返回（OK）。

#### 3.4 资源风险
- `formulaWidthMeasurer` 在 `wrapLongFormulas` 期间会对**每个** `$$` 块各 `build()` 一次 `JLatexMathDrawable` 测宽。题目一大、长公式多（如 2.jpg 这种），会反复创建大量 Bitmap Drawable，OOM 风险升高。
- 当前 `runCatching` 包了 `build()`，崩溃挡住了，但 `runCatching` 返回的 fallback 是按字符估算，逻辑本身不会闪退，**真正闪退是 Markwon 那次 setMarkdown**。

### 计划
按"从主到次、从低成本到高成本"修：

1. **(关键) 给 `JLatexMathPlugin` 装 `errorHandler`**：
   - 调用 `JLatexMathPlugin.create(textSize, latexConfig, errorHandler)`，handler 返回一个兜底 `Drawable`（灰底圆角，显示「⚠︎ 公式无法渲染」），不抛异常。
   - 解决 3.1 主因。

2. **(关键) `MarkdownAnswer.update { }` 整体 `runCatching`**：
   - 任何异常 → `Log.e("MarkdownAnswer", "render failed", e)` + `view.text = 原文 + "\n[渲染失败，已回退为纯文本]"`；
   - 避免未来插件升级引入新抛点时再次闪退。

3. **(重要) 拓宽 `wrapLongFormulas` 的 `$$` 识别**：
   - 判定 `line.trim() == "$$"` 同时接受 `line.trim().startsWith("$$")` + 紧跟内容在同一行（已经在 `wrapInlineLine` 里有，但多行 case 没有）；
   - display 状态机遇到 `$$...$$` 同行（首尾各占一部分）也要正确处理；
   - 多于 1 个空格/制表符都允许。

4. **(重要) `transformEnvironment` 加防御**：
   - 列数上限（例如 `min(maxAmpersands + 1, 6)`），超过给警告并原样返回原 LaTeX（不转 array）；
   - 跳过包含 `\hline` / 非法字符的行；
   - `rows` 全空或仅 `\\` 时直接原样返回。

5. **(可选项) `formulaWidthMeasurer` 改进**：
   - 已经 `runCatching`，但增加：测量后若 `intrinsicWidth` 大于 `maxWidthPx * 3` 直接当 overflow 返回 -1，让 `splitFormula` 按字符估算，避免重复 build 大 drawable；
   - 给测量加简单缓存（按 latex 文本）减少重复。

6. **(可观测) 写本地崩溃日志**：
   - 捕获到 `render failed` 后，把 1KB 左右的「原始内容片段 + 异常类型」追加写到 `getExternalFilesDir(null)/assistant-render.log`（不超过 200KB，自动截断），便于事后定位是哪类回答触发的；
   - 不含用户敏感内容（与现有的 `recovery/` 目录风格一致）。

7. **(回归) 增加单测**：
   - 现有 `FormulaWrappingTest` 之外，添加：
     - `wrapLongFormulas` 对带缩进 `$$` 的处理；
     - `transformEnvironment` 对超长列数 / `\hline` 的处理；
     - 一个能复现闪退的 LaTeX 字符串作为 fixture。

### 暂不动的事
- `sanitizeAssistantLatex` 主体逻辑不变（已经能修好 80% 的情况）；
- 助手回复内容本身（依赖系统提示词约束），不主动重写。

## 实施顺序建议

1. 先做 3.1+3.2 解决闪退（风险最高）。
2. 再做 2 改确认入口交互（纯 UI 改动，风险低）。
3. 最后做 1 表格（要加依赖、需重新构建出包）。

每一步单独构建、跑 `AssistantResponseParserTest` / `FormulaWrappingTest` / `EnglishEntryDaoTest` 回归。
